# TLS Certificate Expiry Monitor

[![cert-monitor](https://github.com/OWNER/REPO/actions/workflows/cert-monitor.yml/badge.svg)](https://github.com/OWNER/REPO/actions/workflows/cert-monitor.yml)

> Replace `OWNER/REPO` in the badge URL with your own repository path.

A daily GitHub Action that opens a real TLS connection to every host in `domains.yml`, reads the
certificate's **expiry date, issuer and SANs**, classifies it, and:

- opens (or updates) a **GitHub issue** with a table of host / days left / status,
- **closes that issue automatically** once everything is healthy again,
- **fails the run** if any certificate is critical or failed, so the badge above turns red.

The checker is ~400 lines of Python using only the standard library (`ssl`, `socket`), packaged in a
Docker image. No cloud account, no secrets, no Kubernetes. The demo runs entirely on localhost.

| Status | Rule (whole days left, rounded down) | Run result |
|--------|--------------------------------------|-----------|
| 🟢 `ok` | more than 30 days | pass |
| 🟡 `warning` | 30 days or less | pass (issue is opened) |
| 🔴 `critical` | 7 days or less | **fail** |
| ⛔ `failed` | expired, handshake failure, or failed trust check | **fail** |

## Quick start (local)

Python 3.9+ is enough; Docker is optional.

```bash
python3 cert_checker.py --config domains.yml
```

```
HOST                  DAYS  STATUS  EXPIRES                  ISSUER
github.com:443        41    OK      2026-11-24 23:59:59 UTC  Sectigo ECC Domain Validation Secure Server CA
...
0 failed, 0 critical, 0 warning, 4 ok
```

Reports are written to `reports/report.json` and `reports/report.md`. The exit code is `0` when
healthy and `1` when anything is critical/failed (`2` for a config error). Use `--fail-on warning`
to be stricter.

With Docker:

```bash
docker build -t cert-checker .
docker run --rm -v "$PWD:/work" cert-checker --config /work/domains.yml --out /work/reports
```

## Configuration: `domains.yml`

```yaml
warn_days: 30       # optional, default 30
critical_days: 7    # optional, default 7
timeout: 10         # optional, seconds per connection

hosts:
  - github.com                 # port 443
  - example.com:8443           # host:port shorthand
  - host: intranet.lan         # full form
    port: 443
    verify: false              # skip chain + hostname check (self-signed / internal CA)
```

The checker ships with a tiny parser for exactly this YAML subset so it needs no `PyYAML`.
Unknown keys and malformed lines produce a clear `config error: line N: ...` message.

`verify` (default `true`) controls whether the certificate must also be **trusted** (valid chain
and matching hostname). With `verify: true`, an untrusted or mismatched certificate is `failed`
even if it has plenty of days left. Expiry is always checked either way.

## The demo: red run, then green run

The Compose stack runs one nginx container with four HTTPS listeners, each using a self-signed
certificate generated by OpenSSL with a deliberately chosen lifetime:

| Port | Certificate | Expected result |
|------|-------------|-----------------|
| 8441 | 90 days left | 🟢 ok |
| 8442 | 20 days left | 🟡 warning |
| 8443 | 3 days left | 🔴 critical |
| 8444 | expired 5 days ago | ⛔ failed |

### Locally

```bash
# 1. Broken certificates -> red
./demo/gen-certs.sh broken
docker compose -f demo/docker-compose.yml up -d nginx
docker compose -f demo/docker-compose.yml run --rm checker      # exit code 1
echo $?

# 2. "Renew" them and reload nginx -> green
./demo/gen-certs.sh renewed
docker compose -f demo/docker-compose.yml exec nginx nginx -s reload
docker compose -f demo/docker-compose.yml run --rm checker      # exit code 0

docker compose -f demo/docker-compose.yml down
```

(`gen-certs.sh` uses `openssl ca -selfsign -startdate ... -enddate ...` because
`openssl req -x509 -days N` cannot produce an already-expired certificate.)

### On GitHub (this is your proof)

1. Push the repo, enable Actions, and fix the badge URL.
2. **Actions → cert-monitor → Run workflow → `demo-broken`**
   The run goes **red**, the job summary shows the table, and an issue labelled `cert-monitor`
   titled *TLS certificate alert* is opened. Screenshot both.
3. **Run workflow → `demo-renewed`**
   The run goes **green**, the issue gets a "healthy again" comment and **closes itself**, and the
   badge turns green. Screenshot these too.
4. Finally, run `production` (or just wait for the daily cron) so the badge reflects your real
   `domains.yml`. The badge always shows the most recent run.

| Trigger | What it checks |
|---------|----------------|
| `schedule` (daily 06:17 UTC) | `domains.yml` |
| `push` to `main` (non-Markdown changes) | `domains.yml` |
| `workflow_dispatch` | `production`, `demo-broken` or `demo-renewed` |

## How the workflow works

1. Run unit tests.
2. Run the checker in Docker (`set +e` so later steps still run), saving its exit code.
3. Append `report.md` to the job summary and upload `reports/` as an artifact.
4. `cert-issue.js` reads `report.json`:
   unhealthy → create or update the issue; healthy → comment and close it.
5. If the checker's exit code was non-zero, fail the job explicitly. That is what turns the badge red.

Permissions are minimal: `contents: read`, `issues: write`. No secrets are used.

## Tests

```bash
python3 -m unittest discover -s tests -v
```

Covers the classification boundaries (31 / 30 / 8 / 7 days), config parsing and error cases,
report rendering, and end-to-end checks against throw-away TLS servers started on localhost
(ok / warning / critical / expired / unreachable / untrusted, plus CLI exit codes).

## Design notes and limitations

- **Why two connections?** A verifying handshake refuses expired or self-signed certificates, so
  the checker first reads the certificate *without* validating it (to always get dates, issuer and
  SANs), then does a separate verified handshake only when `verify: true`.
- **Whole days, rounded down.** `30.9` days left displays and classifies as `30` (warning). The
  alerts err on the early side.
- **Private decoder.** The standard library can only decode certificates from a file, so
  `decode_der()` uses `ssl._ssl._test_decode_cert`, a private helper that CPython's own test-suite
  relies on and that has been stable for many releases. If it ever disappears, the unit tests fail
  loudly. The alternative is shelling out to `openssl x509`.
- Checks the **leaf** certificate only (not intermediates), over direct TLS. STARTTLS protocols
  (SMTP, IMAP) are not supported.
- GitHub-hosted runners can only reach publicly reachable hosts. For internal services, use a
  self-hosted runner.
- GitHub disables scheduled workflows after 60 days without repository activity; any push or manual
  run re-enables them.
